# Silver Glider Events — Master Reference

**Last updated:** September 21, 2026 (v1.0.126)

## 1. What it is
Silver Glider Events is a lightweight tool for creating beautiful event pages, collecting RSVPs, linking guests to third-party ticket providers, and sending reminders. It is **Version 1** of a bigger platform, built for independent hosts, promoters, artists, venues, and private gatherings.

- **Live site:** https://silvergliderevents.com (custom domain; the Railway URL https://silver-glider-events-production.up.railway.app still serves the same app)
- **Silver Glider Events does not process ticket payments.** Hosts can publish Free RSVP events, use external ticket links, or select a feature-gated Silver Glider Commerce handoff. Checkout, inventory, orders, issued tickets, verification, refunds, payouts, and Stripe Connect belong exclusively to the separate Commerce service.

## 2. How to use it (organizer)
1. Go to the site and click **Create your event** → enter your phone number and the six-digit Twilio Verify code. **Use email instead** keeps the original magic-link path available.
2. The first verified phone also requires a separate email code so it can bind safely to the existing Silver Glider identity. Returning non-admin creators skip that one-time binding step.
3. You're taken directly to the four-field event starter. No password is created.
4. Fill in title, date, time, and the unified **Location** search. Google Places accepts establishments and normal street/residential addresses; address-only locations may add an optional friendly Location Name, and manual entry remains available. Then choose a presentation:
   - **Standard** uses a cover image, full event details, and an optional gradient/effect background. **Choose image** opens the local uploader; **Browse free photos** opens Unsplash. The picker separates 4 **Gradients** (**Midnight**, **Aurora**, **Sunset**, **Ocean**) from the ordered **Effects** (**Halloween**, **The Last Guest**, **Disco**, **Fog**, **Kraft paper**, **TV static**, **Liquid Stardust**, **Color Static**, **After Hours Saloon**, **Match Photo**). Match Photo derives a dark, readable palette from the selected artwork. Moving effects loop with poster, reduced-motion, and data-saving fallbacks.
   - **Flyer** accepts one uncropped poster/flyer upload and renders an isolated, centered, poster-first public page. An optional designer name and Instagram handle appear only after a flyer exists; the subtle public credit prefers the normalized Instagram handle. The default Flyer backdrop is the fixed, darkened plaster-wall image at `public/images/flyer-plaster-wall.jpg`, while an explicitly selected effect overrides it. The normal RSVP, external-ticket, guest-list, comments, host, calendar, privacy, and organizer-management systems are reused unchanged.
   - The Unsplash picker opens on **Halloween** and includes separate **Fall**, **Silver Glider Picks**, and supporting visual collections. Search runs only when a pill, Enter, or Search is selected and uses a bounded server cache to reduce API requests.
   - An optional **Presented by** name. The first one creates a reusable public host page at `/h/<slug>`; future events automatically reuse it. **Settings** controls the host name, unique slug, large header image, logo/avatar, bio, Instagram handle, and website URL. The signed-in account email remains the only email field until a separate Booking Email feature is designed.
   - Description, category, capacity, admission, and visibility. Admission supports Free RSVP, External tickets with the established displayed price and optional outbound URL, and a feature-gated Sell tickets with Silver Glider handoff backed only by a Commerce event reference. **Public** and **Private — Link Only** events can independently enable a first-name/avatar guest list, one named +1 per RSVP, and text-only attendee comments under **Guest experience**. Under **Automatic texts**, the independent **Day-before reminder** switch defaults off and explains that cost follows the number of guests who opt in. Private events stay off public host pages, discovery, and The Line while remaining accessible to anyone with the direct link. **Secret Show Mode** remains private-only and adds a six-character access-code gate; automatic texts are unavailable for Secret Shows.
   - On phones, creation is an app-like task flow rather than the desktop form stacked into one long page. Quick Create moves through Title, Date & time, and Location, then opens the live editor. The full editor uses a compact summary hub with focused Appearance, Event details, Description, Event vibe, Admission, Visibility, Capacity, Guest experience, and Reminders screens; Flyer designer credit and Effects open as their own Appearance sub-screens. Admission offers Free RSVP, External tickets, and the one-tap Silver Glider ticketing waitlist. Visibility presents Public, Private link only, and Secret Show as peer choices; Secret Show explains that it is private and requires a six-character code. Each task reuses the original controls and shows a live summary; validation opens and focuses the task that needs attention. On desktop, create/edit remains a wide two-column workspace with **Page Design** beside **Event Information**. Standard background options stay visible after a cover is selected, so hosts can choose imagery before or after choosing the page background.
5. **Publish.** You get a shareable link and a mobile-first public page. The owner-only **Edit event** control opens a right-side rail on desktop and a full-screen task hub on phones. Quick-create drafts receive a short guided sequence; returning hosts can jump directly among focused Appearance, Event details, Admission, Visibility, Capacity, Guest experience, and More tools views. Image, background, details, location, flyer credit, and guest-setting changes preview immediately but persist only after **Save changes**; Cancel restores the saved event. When a published event with confirmed RSVPs changes date, start time, or location, both editors summarize the exact change and ask the host to **Save & notify** or **Save without email**. QR download remains an organizer promotion tool and is not shown on the public event page.
6. On phones, **Edit event** is the first prominent management action. The remaining hub tasks are **Overview**, **Guests**, **Promote**, **Photos** when available, and **Event actions**, each opening one focused area with a consistent back action and Preview. Browser Back and forward traverse focused Quick Create, editing, management, and Host Page Settings tasks before leaving; unfinished Quick Create fields and the active step recover within the same browser session until creation succeeds. Event actions directly displays Duplicate, Cancel, and Delete without another disclosure. Desktop retains the established artwork-and-actions layout and toolbar. Duplicate shows an immediate working state, prevents repeat requests, and opens the new draft directly in the editor; failures restore the action and show an error. Cancelling asks whether to email every confirmed RSVP, and the management page shows the latest update/cancellation delivery status. Familiar Faces uses verified photos or stable playful emoji fallbacks, leads with each person's name, and shows `RSVP’d`, `Invited`, `Can’t make it`, or `[friend]’s +1`; search and **Export CSV** remain available. From an old published event, select individual eligible people or all, choose one owned upcoming published event, review, and send one artwork-led email with one **RSVP** action. Every confirmed primary RSVP with an email is eligible for a direct invitation even when the separate host-update opt-in is false; named guests, cancelled RSVPs, host opt-outs, existing target attendees, and already-notified recipients are excluded and rechecked server-side. On an upcoming event, Familiar Faces adds **Invite your people**: every eligible person from your past events as one face each (labeled with the event you know them from, regulars first), filtered by the same search box and an optional past-event dropdown. Tap faces, review “Invite N people to [event]?”, and send; nothing is pre-selected, there is no once-per-event limit, and named +1s show a **Share link** button instead of being emailed. The Promote panel’s **Invite Familiar Faces** row jumps to that section. **Promote your event** continues to handle sharing, QR download, the host-approved **Update my followers** review, and **The Line**. Follower updates always include eligible emails and may include separately consented paid texts when the host has enough credits; the preview shows exact audience and cost before the one-shot send. An enabled **Day-before reminder** always shows its current opt-in count; after at least one guest opts in it also shows exact estimated credits and balance, with **Add funds** only when the balance is short. A fully funded audience sends automatically at 4 PM event-local on the day before the event. To declutter the event list, **swipe an event left to Archive** (reversible — guest data always kept); permanent delete remains double-confirmed.
7. **Submit to The Line** to request a feature in the Silver Glider SMS/marketing channel (an admin reviews it).
8. Use the quiet **Feedback** button in the bottom-right of any signed-in app page to report a bug, suggestion, or other feedback. Reports automatically include the authenticated host, page, related event when applicable, and browser context.

**You stay logged in for 30 days** on your device (and it auto-extends while you're active), so you won't need a new email every time.

## 3. How guests use it
- Open the event link → tap **RSVP**. On mobile, the RSVP action docks at the bottom until the inline action/form is reached.
- The compact form asks for name first and progressively reveals email. When the host has enabled a day-before text reminder, a separate unchecked event-specific opt-in appears; checking it reveals and requires the phone field. Host-update email consent remains independent under **More options**. Guests do not create an account, and the expanded RSVP form can be collapsed.
- Opted-in guests receive one text the day before the event. Its private, expiring link restores the same event-scoped attendee access used by the confirmation email and remembers verified phone access for that RSVP; it does not create a profile or general account.
- Immediately after RSVP, the event opens a focused confirmation dialog on desktop or bottom sheet on mobile with the answer, event/host/date/time/location, personal calendar action, and in-place answer change. Closing it leaves a compact **View RSVP** status card. The artwork-led confirmation email with its `.ics` attachment is a backup and uses one **View or change RSVP** action back to this same personal confirmation. When the guest's reusable identity has no photo, a secondary **Add your photo** block opens the one-time authenticated `/add-photo` page; saved photos suppress the block.
- They receive **reminder emails** the day before (4pm) and day of (9am), in the event's time zone.
- If the host chooses to notify after changing the date, start time, or location—or after cancelling—the primary email on every confirmed RSVP receives a one-way transactional notice even when ordinary reminders were declined. Update and cancellation messages include the attendee's secure event link and a versioned calendar attachment. Named guest emails are not contacted separately in V1.
- If the event hits capacity, RSVPs stop and it shows "Event full."
- Guests can cancel their RSVP from a link in their email (which frees a spot).
- The on-page success state is **You’re going** (or **You can’t make it**) in the reusable confirmation surface; guests do not need to open email to confirm completion.
- Recognized guests are event-scoped through a personal invitation/RSVP token or an authenticated account. Once answered, the compact event card shows **✓ You’re going** (or **You can’t make it**) with **View RSVP**. **Not [name]? RSVP as yourself** removes that personal URL from the event view or forgets the applicable browser identity.
- After answering, guests see a quiet **Host your own event →** link (success card, returning-guest status card, and the confirmation email footer). It goes to `/login?next=/events/new`, so signed-in people land straight in Create Event.
- Every personal link in the guest’s own emails (confirmation **View event**, the manage link, text reminders, Familiar Faces invitations) opens the event showing their answer. In a browser that doesn’t know them, “You’re already on the list” offers **Manage my RSVP here** with a 6-digit code.
- When a browser can’t prove an RSVP is the guest’s (a new phone, or rejoining after cancelling), the page emails a 6-digit code and the guest types it right there — no account, and no hunting for the confirmation email.
- When a private host enables **Allow guests**, an RSVP can include one named guest with an optional email. Capacity and the displayed attendance total count both the attendee and guest.
- When enabled, the public guest list shows first names only. A fresh RSVP unlocks the comment wall immediately on that browser; the confirmation-email link restores attendee access on another or returning device. Attendees can post or delete their own 300-character comments, while the event host can delete any comment. Existing-email attempts never grant access based on email knowledge alone.
- Signed-in RSVP forms reuse the saved account name and email. When identity is verified by the signed session or the attendee's private manage token, the saved personal RSVP photo appears in the guest list; arbitrary email entry cannot claim another account's image.
- Guest-list previews show first names beneath avatars for one to five attendees. At six or more, they switch to compact overlapping circles; **See everyone** opens the accessible desktop modal or expands the full list inline on mobile.
- Secret Shows reveal no title, date, venue, description, metadata, or other event details until the correct code is entered. A signed, time-limited browser cookie remembers the unlock; afterward the guest sees the normal private event page and all enabled RSVP, guest-list, named-guest, comment, share, and calendar features.

## 5. Login & security (plain English)
- Login has **no passwords**. Ordinary sign-in, RSVP identity, and Follow Host stay email-first. The high-intent **Create your event** journey is phone-first: Twilio Verify proves the phone, then an unbound number also requires the existing browser-bound email code before it can attach to the shared identity. Phone proof alone never creates a new user or session and identity collisions never auto-merge. Twilio Verify also proves bound non-admin phones before opening the same 30-day account session; admins remain email-only, **Use email instead** remains available throughout, and **Sign out of all devices** revokes the phone credential so email remains effective recovery.
- Authentication phone credentials live in `account_phone_credentials`; RSVP and Follow Host phones remain separate messaging-consent records and must never be copied into or inferred as login credentials.
- After the first login, a secure **30-day session** keeps you signed in on that browser; it auto-refreshes while you're active.
- **Sign out** ends the session on that browser and forgets any remembered RSVP guest there. **Sign out of all devices** (Settings → Account) rejects every older session everywhere. Requesting too many sign-in emails, or guessing codes, is rate-limited; five wrong codes lock that request.
- The **Add your photo** link in RSVP confirmations only opens the photo page — it never signs anyone into the dashboard.
- Public event pages are open to everyone; the organizer dashboard is protected. Secret Shows are private link-only events with a separately stored scrypt code hash, signed versioned unlock cookies, and per-session/per-IP attempt limits. Replacing the code invalidates prior unlocks.
- Public RSVP submissions and confirmation-email resend attempts are rate-limited to reduce spam and fake capacity filling.
- Host/admin-rendered text is escaped before insertion into HTML, and executable URL schemes are rejected. Database IDs from the authenticated session—not editable names or emails—are the authorization source of truth.

## 6. Tech summary (for a developer)
- **Stack:** Node.js + Express 5, PostgreSQL, server-rendered HTML + vanilla JS. No build step, no framework.
- **Repo (local):** `~/silver-glider-events`
- **Entry point:** `src/index.js`
- **Key folders:** `src/routes/` (auth, events, public event/RSVP flows, isolated public host pages, uploads, photos, Stripe and legacy PayPal webhooks, SMS credits, paid SMS notifications, admin), `src/lib/` (mailer, server-only Twilio SMS transport/lifecycle copy, Stripe SMS Checkout, legacy PayPal client, SMS credit ledger, session, shared public HTML, calendar/ics, unsplash, cloudinary, slug, csv), `src/jobs/reminders.js` (scheduled email reminders), `src/jobs/event-notifications.js` (critical email update/cancellation delivery and retry), `src/jobs/previous-guest-invitations.js` (reviewed past-guest email delivery and retry), `src/jobs/sms-notifications.js` (paid Twilio delivery/retry/audit), `src/views/` (HTML pages), `public/` (CSS + JS/assets).
- **Database:** auto-migrations run on startup from `src/db/migrations/*.sql`. `users.id` is now the canonical person key, while `organizers.id = organizers.user_id = users.id` preserves the existing profile/session compatibility contract. `user_identities` owns normalized email/phone/future Google identifiers; `user_identity_verifications` keeps scoped proof provenance; `user_identity_conflicts` quarantines ambiguous legacy ownership without merging. Core product tables remain organizers, magic_link_tokens, events, event_secret_codes, rsvps, event_comments, message_log, event_notification_batches, previous_guest_invitation_batches, sms_notification_batches, sms_notification_recipients, line_submissions, feedback_submissions, host_invitations, host_follows, event_photos, commerce_feature_interests, sms_credit_purchases, sms_credit_transactions, stripe_sms_webhook_events, and paypal_webhook_events.
- **Current migrations:** `001` through `055_admin_done_for_you_foundation.sql`.
- **Health check:** `GET /health` returns `{status:"ok", version:"...", sha:"..."}`.
- **Release version:** `package.json` is the canonical semantic version, production commits receive matching annotated Git tags, and `CHANGELOG.md` records user-facing releases. `/health` returns both `version` and `sha` for deployment verification.

## 8. How to deploy a change
Production may contain promoted events, so the MVP workflow is **local first, production second**:

1. Run and test the change locally at `http://localhost:3100` against `postgresql://localhost:5432/sge_dev`.
2. Keep `NODE_ENV=development` and `REMINDERS_ENABLED=false` locally. Never use the Railway production database for development or test data.
   Local cover uploads automatically go to `sg-events-dev/covers`; production covers remain in `sg-events/covers`.
3. Verify `/health` and the specific organizer/guest flows affected by the change.
4. Commit only after local testing passes. Push when GitHub credentials are available.
5. Before deploying, explicitly report whether the release affects existing live event pages, shared Cloudinary assets, guest lists/RSVPs, outgoing emails/reminders, or only new/local behavior. Replacing an asset at an existing Cloudinary URL affects every live event using it.
6. Deploy to production from `~/silver-glider-events`:

```
git rev-parse --short HEAD > .git-sha && railway up . --path-as-root --service silver-glider-events
```

The explicit application path and `--path-as-root` prevent the parent workspace's separate image ignore rules from stripping PNG/JPEG assets. Do not shorten this command.

7. Verify `curl https://silver-glider-events-production.up.railway.app/health`. The `version` should match `package.json`, the `sha` should match `git rev-parse --short HEAD`, and the status must be `ok` rather than `asset_error`. Then perform a small, non-destructive production smoke test. (`.git-sha` stays a tracked-but-modified file each deploy — that's expected.)

**Current machine note:** GitHub CLI authentication is active for `code666now` and Git operations use HTTPS. If a future push fails, check `gh auth status` before changing the remote. This remains separate from Railway: a successful GitHub push does not deploy production, and a successful Railway deployment does not prove the repository backup is current.

**Commerce admission foundation (September 3, 2026):** migration `024_commerce_admission_types.sql` adds nullable `events.commerce_event_id` and accepts canonical `free_rsvp`, `external_tickets`, and `silver_glider_tickets` values while retaining legacy admission values. The editor exposes Free RSVP, External tickets, then Sell tickets with Silver Glider as a readable **Coming soon** choice until `COMMERCE_ENABLED=true` and a Commerce base URL are configured. **Ticketing launch interest (updated September 17, 2026):** migration `025_commerce_feature_interest.sql` adds a separate `commerce_feature_interests` table for explicit, reversible, one-time Commerce launch consent. Signed-in hosts see one **Join the waitlist** action under the Coming soon admission choice; no duplicate identity form is shown because the authenticated organizer email is reused. Success updates in place to **You’re on the list** with “We’ll contact you at your account email when ticketing is available,” and a quiet leave action immediately excludes the host. Opting in twice remains one row, and this account-level interest never makes an event draft dirty. Super Admins use `/admin/ticketing` to review interested, awaiting, and notified hosts and to send a private test email. The launch button stays locked until Commerce is fully configured and requires an explicit confirmation. Atomic delivery claims, stale-claim recovery, success timestamps, and per-recipient errors make retries safe without emailing a delivered host twice. Nothing sends automatically, and RSVP updates, Host follows, and general marketing consent remain independent.

**Follow Host (unified in v1.0.102):** `organizers` remains the shared email identity table; following never creates a public Host Page. Signed-in people follow immediately, while signed-out people use the existing code/link verification and 30-day session. One host-scoped `/h/<slug>?follow=1` link opens the same Follow flow. Hosts share that URL through the native phone share sheet on touch devices or an app-owned desktop dialog with Email, Pinterest, Facebook, X, and Copy link. Email updates are included through explicit, versioned consent. If the host currently owns SMS credits, the form also offers a separate unchecked text option and reveals the phone field only when selected. SMS consent has its own disclosure, normalized number, source, version, and timestamp. Existing follow rows are deliberately not backfilled. A host-approved public-event update combines eligible legacy email subscribers and explicit Follow email subscribers, dedupes/suppresses them, and can add only explicitly consented text followers after previewing exact segment cost. SMS uses the existing atomic wallet, batch/recipient audit, retry, and STOP machinery. Unfollow writes the shared host-level email suppression and disables text consent. RSVP, Familiar Faces invitations, and event-specific reminders stay independent.

**Photo picker (developer note):** Category presets live in `public/js/event-form.js`. **Halloween** is the initial collection, followed by **Fall**, **Silver Glider Picks**, and supporting visual categories. Each pill issues one tuned Unsplash search only when the user selects the pill, presses Enter, or uses Search; typing alone does not call the API. `/api/photos/search` accepts a capped `per_page` value (1–24). `src/lib/unsplash.js` caches search responses in memory for 30 minutes and evicts the oldest entry once the cache reaches 200 keys. The cache is per server instance and does not require Redis at the current single-instance scale.

**Background system (developer note):** `events.background_theme` holds one key—an MVP gradient (`midnight`, `aurora`, `sunset`, `ocean`) or an effect (`halloween`, `last-guest`, `disco`, `fog`, `paper`, `static`, `liquid-stardust`, `color-static`, `saloon`, `adaptive`). `adaptive` is labeled **Match Photo** and derives the Standard page palette from its artwork. `violet` and `ember` are no longer offered or accepted for new saves, but `src/routes/public.js` retains legacy rendering support for already-published events. **Standard pages** use `.bg-theme .bg-<key>` and may receive an image-derived palette from `public/js/public-event.js`; choosing a cover does not hide the background controls. **Flyer pages** are isolated in `src/views/event-public-flyer.html` and `public/css/event-public-flyer.css`; without an explicit effect they use the fixed grayscale plaster photograph `public/images/flyer-plaster-wall.jpg` under a dark readability veil. Explicit effects render via `.event-bg.fx-<key>` and override the Flyer default. Kraft paper and After Hours Saloon are still images; TV static is a canvas; Halloween, The Last Guest, Disco, Fog, Liquid Stardust, and Color Static use optimized Cloudinary video loops. Liquid Stardust and Color Static add an end-to-start crossfade to hide source-video seams. Motion respects hidden tabs, autoplay failure, data-saving mode, and reduced-motion preferences. Adding an effect requires a whitelisted key, asset mapping, picker swatch, and fallback; no schema change.

**RSVP confirmation email (developer note):** `src/lib/mailer.js` has a confirmation-only 620px presentation-table layout; reminders and other shared emails keep their established layout. Cloudinary landscape covers/flyers are delivered as Outlook-safe JPEGs on a 620×560 predominant-color padded canvas, preserving the original composition; portrait art keeps its aspect ratio. The email is deliberately a backup: artwork, title, optional host/vibe identity, **You’re going** status, and one artwork-accented **View or change RSVP** button lead to `/r/:manageToken/event`. Full event details, calendar action, and answer editing live in the shared on-page confirmation dialog/sheet. The `.ics` attachment, optional Add Photo block, reminder note, and quiet Silver Glider footer remain.

### Sign-in, sessions, and returning guests — rules to keep (v1.0.85)

- **`GET /auth/verify` must stay read-only.** It renders the Continue page via `peekLink`; only `POST /auth/verify` (`consumeLink`) signs in. Email scanners open every link — a GET that consumes turns real sign-ins into "expired".
- The Continue page uses `Referrer-Policy: same-origin`, not `no-referrer`: with `no-referrer` browsers send `Origin: null` on the POST. The login-CSRF check (`sameOriginPost`) trusts `Sec-Fetch-Site` first, then `Origin`.
- `magic_link_tokens.token` stores **SHA-256 hashes** (`tokenHash`). Codes are HMAC'd, bound to the requesting browser by the `sge_sign_in` cookie (`request_hash`), and lock after 5 wrong tries. All of this lives in `src/lib/sign-in-challenges.js`; create challenges only through `createSignInChallenge`.
- **Account ownership checks read `req.sessionAccount`**, resolved once per request by `sessionMiddleware` (`src/lib/session.js`), which enforces `organizers.sessions_valid_after`. Don't call `parseSession` directly in routes — it can't see revocation. Session cookies now carry an issue time (`id.iat.exp.sig`); the old `id.exp.sig` format is still accepted.
- Cookies are **appended** (`res.append('Set-Cookie')`), never set, so one response can carry several.
- Guest verification has a scope: `guest_sessions.verified_event_id`; typed codes (`intent: 'verify_guest'`) verify globally (NULL). Familiar Faces `/g/:token` links no longer create guest sessions: the durable, hashed token is resolved directly for its target event and is passed through the personal event URL. Never treat that token as an account session.
- A successfully typed browser-bound `verify_guest` code also establishes the normal `sge_session` account session. This is the deliberate bridge from lightweight RSVP identity to global authentication. First RSVP still creates only `sge_guest`; personal RSVP/invitation links, text-reminder links, and Add Photo access must never create `sge_session`.
- The Add your photo link uses `intent: 'add_photo'` and sets the short-lived `sge_photo` cookie, accepted only by `requirePhotoAccess` on `/add-photo`, `/api/me`, and `/api/uploads/avatar`. Never let it create `sge_session`.
- When a browser can't prove it owns an RSVP, routes answer `409 { error: 'verification_required', maskedEmail }`; `public/js/public-event.js` shows the inline code (`confirmItsYou`) and retries. Reuse that instead of sending people to their inbox.
- **Invite your people** (v1.0.87) is served by `GET /api/events/:id/familiar-faces/people` (search, `sourceEventId`, `offset`; 48 per page; returns no emails) and `POST /api/events/:id/familiar-faces/people/invite` (`faceIds` like `rsvp:123`). Eligibility lives in `PAST_RSVPS` and `connectedToTarget()` in `src/routes/events.js`; send groups recipients into one `previous_guest_invitation_batches` row per source event so each email names the right past event. The old target-first `GET/POST /api/events/:id/previous-guests*` routes and their `eligiblePreviousGuests` helper were removed; a test keeps them from coming back. The batch table, the `previous_guest_invite` message type, the delivery job and the email template are still shared by Invite your people and Familiar Faces.
- Local dev and tests: with no `RESEND_API_KEY`, emails land in `mailer.devOutbox` (and the console). Integration tests read links and codes from there — the database only has hashes. Test helpers `followSignInLink` and `resetRateLimits` are at the top of `test/integration/public-flows.test.js`. Confirmation emails run through `runInBackground` (in `public.js`) and the suite calls `settleBackgroundWork()` before every reset — without that, a late confirmation deadlocks the next test’s TRUNCATE.

This repository is a continuation of the same Silver Glider Events project, not a restart. Treat the code, migrations, tests, and current production health response as the source of truth.

### Context and working rules to preserve

- Read this file first, then run `git status` and `git diff`, and inspect the relevant implementation before editing.
- Preserve unrelated work and prefer small additive improvements with mature copy, restrained hierarchy, progressive disclosure, accessibility, and desktop/mobile verification.
- Use `apply_patch` for code and file edits. Run `git diff --check` and `npm run check`; integration tests must use the dedicated local `sge_test` database.
- Production releases update `package.json`, `package-lock.json`, `CHANGELOG.md`, and a matching annotated Git tag. Update `.git-sha` to the release commit before `railway up . --path-as-root --service silver-glider-events`, leave `.git-sha` uncommitted, and verify both production health URLs and the critical public image URLs.
- Railway deployment and GitHub backup are separate operations. Push only tested commits and tags; never treat a GitHub push result as proof of production deployment.
